# Restricted customer billing portal

This module issues Stripe billing-portal sessions for a named current customer with explicit **whole Stripe Customer** billing authority. Tenant membership, engagement approval, invoice ownership and finance staff status do not imply that permission. The portal may expose invoices across engagements and let the customer pay them or change their customer-wide default payment method. It cannot be used as an engagement audience filter.

Owned files: `worker/workspace/portal/{provider,secrets,service}.mjs`, `src/workspace/portal-ui.mjs`, `tests/workspace/portal.test.mjs`, this guide and `db/workspace/migrations/20261031162901_billing_portal.sql`. The migration was generated by local Supabase CLI v2.106.0. No remote migration or provider call was performed during implementation.

## Provider contract and qualification

The existing Stripe helper pins `2026-10-28.endive`. This module preserves that pin. It uses the platform/direct merchant key architecture already implemented by the helper; Connect per-request `Stripe-Account`, Accounts v2 `customer_account` and `on_behalf_of` are unsupported. Do not silently add them or infer they isolate engagement/payment-method access.

Every session issuance performs GET `/v1/account`, GET `/v1/customers/{customer}` and GET `/v1/billing_portal/configurations/{configuration}`. It requires exact server-owned merchant, environment, sandbox identity, Customer, configuration, return URL and qualified configuration fingerprint. `livemode=false` alone does not identify a sandbox. The runtime `STRIPE_SANDBOX_ID` is operator-qualified custody/configuration evidence, not a claim that Stripe returned or cryptographically verified the sandbox ID.

The explicit nondefault active configuration must return all six feature objects:

```json
{
  "invoice_history": {"enabled": true},
  "payment_method_update": {"enabled": true},
  "customer_update": {"enabled": false},
  "subscription_update": {"enabled": false},
  "subscription_cancel": {"enabled": false},
  "subscription_pause": {"enabled": false}
}
```

`login_page.enabled` must be false and its URL null. `default_return_url` must equal the fixed approved HTTPS return URL; `metadata.policy_version` must equal the reviewed version. Unknown feature objects, omitted flags or changed effective nested fields fail closed. The fingerprint covers identity, mode, active/default status, application, return URL, all feature data, login page and policy version. It includes the payment-method configuration selection; omission of a pause/permission flag is never treated as false. Metadata is merely a policy label; effective readback is checked separately.

The official SDK schema includes `subscription_pause` while the shortened REST example omits it. A live pin returning that shortened/incomplete shape fails qualification. Resolve the schema discrepancy; do not relax the check to make it pass. Configuration administration can race readback; pre/post checks narrow but cannot eliminate that race. Restrict provider configuration editors and requalify changed versions.

The only session POST is:

```http
POST /v1/billing_portal/sessions
Stripe-Version: 2026-10-28.endive
Idempotency-Key: wm:portal:<operation UUID>:<dispatch nonce>
Content-Type: application/x-www-form-urlencoded

customer=cus_...&configuration=bpc_...&return_url=<fixed encoded HTTPS URL>
```

No browser-controlled Customer, configuration, merchant, `flow_data`, `after_expiration`, `customer_account` or `on_behalf_of` is accepted. Response identity, mode, configuration, return URL and created time must match. Recovery/flow/account overrides must be null or absent. Only `https://billing.stripe.com/p/session...` bearer URLs qualify; custom portal domains require a future reviewed exact-host contract.

Sources checked: [configuration object](https://docs.stripe.com/api/customer_portal/configurations/object), [official generated configuration schema](https://raw.githubusercontent.com/stripe/stripe-node/master/src/resources/BillingPortal/Configurations.ts), [create session](https://docs.stripe.com/api/customer_portal/sessions/create), [Stripe idempotency](https://docs.stripe.com/api/idempotent_requests), and saved `BILLING-PORTAL-BOOTSTRAP-REVIEW.md`. The expanded configuration query URL was inaccessible through the research tool; the official generated schema supplied the explicit pause field. Supabase's markdown changelog fetch was unsupported by that tool; its [breaking-change index](https://supabase.com/changelog?types=breaking-change) was checked instead. The module grants only explicit RPC execution and no raw table access, compatible with current exposure defaults.

## Trusted setup and narrowly scoped grants

`registerPortalBinding(env, org, binding, expectedVersion, overrides)` is **server setup only**, never an endpoint accepting customer/browser JSON. It verifies existing provider objects and calls `wm_portal_binding_register`; it creates or updates no Stripe object. Supply an independently approved exact binding, qualification evidence and expected local version. No automatic fingerprint repair occurs during normal issuance.

The binding must exactly match the existing `wm.billing_accounts` row and generation. Existing billing and portal uniqueness prevent cross-business Customer/account/mode reuse. Merchant/Customer/environment/sandbox identity is immutable for an existing portal binding. Configuration/version changes invalidate earlier customer grants; use explicit revocation and a fresh grant for the new version. Identity remapping is a separate reviewed migration/workflow, not an automatic portal repair.

`wm_portal_grant(org,input,key)` requires recent authentication, current direct finance AND people operator authority and MFA through existing access checks. It grants only a verified current non-viewer customer membership for this exact binding/version. It does not create membership, staff privileges or spending/approval authority. New grant example:

```json
{"user_id":"<verified customer UUID>","binding_version":1,"expected_version":0,
 "revoke":false,"ends_at":"<explicit future timestamp, at most one year>",
 "evidence":"<reviewed whole-customer billing authorization>"}
```

Revocation uses the same user, current binding version, exact grant expected version and `revoke:true`. It appends a critical authority receipt. Only one unrevoked grant exists per user/binding. Expired or obsolete grants must be explicitly revoked before replacement. No first-login/bootstrap shortcut exists.

Four private RLS tables hold binding, explicit grant, immutable request projection and ephemeral encrypted URL. Raw table access is revoked from public, anon, authenticated and service_role; narrow security-definer functions use empty search paths and current checks. Machine functions require service_role. Human functions require current session, recent authentication and tenant locking.

## Shared kernel and failure sequence

1. `portal.request` accepts only `{expected_version}` plus the normal stable command key. SQL checks current whole-customer grant, original session, verified membership, mapping version, tenant authority/recovery/external generation and open positive-effect control. It creates a `billing_portal_create` operation using existing `wm.enqueue`, outbox job and critical request receipt. There is no second retry ledger.
2. The new `wm_attempt_begin` wrapper checks portal authority and receipt durability, rejects every second registered attempt for that operation, and delegates all normal leasing/attempt creation to the existing function chain. Other kinds keep existing behavior and grants. A frozen kernel permit is stored once on the request so reconciliation journals the **identical original intent bytes**, rather than a later mutated operation/attempt snapshot.
3. The dispatcher persists its existing independent attempt intent; `portalEffect` also idempotently ensures that same intent through `journalAttempt` before POST. It verifies provider configuration and current SQL/independent control again. There is no atomic transaction spanning Postgres, the journal and Stripe.
4. The provider response is validated and its nonsecret session ID checkpointed through `wm_attempt_checkpoint`. Current authority/control and configuration are checked again. If current access changed, the remote result remains historical evidence but the URL is withheld.
5. A sanitized proof returns to the shared dispatcher. The dispatcher persists its independent outcome journal and calls the existing resolve chain. The portal resolve wrapper rejects extra/raw-response fields and verifies immutable identity/fingerprint. The generic critical execution receipt remains part of the normal kernel. URL disclosure waits for that receipt to be independently durable.

The operation uses a dedicated kind rather than `stripe_*`, because existing billing wrappers interpret every `stripe_*` kind as an obligation/refund. Its own context requires positive effects allowed and exact epoch; do not skip those checks when wiring the dedicated kind. Do not rewrite it as a financial obligation or auto-start service billing.

Timeout/error after a possible POST stays unknown in the shared attempt. No automatic new key and no scheduled POST reconciliation. Explicit `portal.reconcile` accepts only `{id}` and rechecks the original user AND original session, current grant/binding/epoch and recent auth. It authorizes a 90-second same-attempt replay window, with a conservative 23-hour maximum age. The adapter uses exactly the original body/context/key and immutable intent. A duplicate reconcile command key does not authorize another replay. Concurrent same-key requests may receive provider conflicts and remain unknown.

Stripe v1 can retain a first executed error response, including a 500; pre-execution failures/conflicts may not be cached. Idempotency keys can be pruned after at least 24 hours. This module's 23-hour gate is a conservative qualified bound, not perpetual exactly-once behavior. No session retrieve/list/revoke contract is assumed. Replaying a cached old session may resolve its creation while leaving its URL unavailable. A separate deliberate fresh request can create another operation but never deletes or resolves the old uncertainty.

Initial dispatch must begin within 15 minutes of request. An expired/cancelled attempt cannot be revived as a new attempt; the customer must explicitly request another operation. Same-key reconciliation still requires the original current session and current authority and is separately bounded as above.

## Bearer URL privacy and disclosure

Only `portal_secrets` stores URL material, encrypted with AES-GCM through the existing envelope helper using a **dedicated** `PORTAL_KEYS` keyring and `PORTAL_KEY_ID`, not recovery keys. AAD binds original user/session, tenant, merchant, sandbox/mode, Customer, configuration fingerprint, authority/external generation, request/attempt/dispatch nonce and exact local expiry. No credentials or raw URL are returned by status, written to operation payloads, command/critical receipts, attempt journals or exports.

Cache lifetime is the earlier of two minutes from receipt and four minutes from provider creation. This is a local disclosure bound; it is not a claim about terminating the remote session. `wm_portal_expire()` removes expired local ciphertext; main must schedule it. URL storage collisions preserve the original record and cannot silently replace a link with another session. Failed storage or post-checks return sanitized creation evidence with `url_available:false`.

`portalRedirect` performs authenticated `wm_portal_disclosure`, independent control and effective configuration verification, decrypts, then repeats current authenticated disclosure and independent control checks immediately before returning a 303. Disclosure requires the same original session, current customer-wide authority, verified operation, durable critical execution receipt and unexpired ciphertext. Response headers are `Cache-Control: no-store, private`, `Pragma: no-cache`, `Referrer-Policy: no-referrer`. Never instrument its Location header, response or URL with analytics/traces/error reports. Main's frontend should submit/navigate directly to this CSRF-protected POST route; do not fetch it through a client JSON/analytics pipeline that exposes or stores the URL.

Local revocation/logout prevents future local disclosures. It cannot recall bytes already disclosed or remotely terminate an opened Stripe session. The saved official review records an unused five-minute session lifetime and activity-based expiration after use; local cache bounds are intentionally shorter. Deactivating a configuration prevents new sessions, not a documented revocation of existing ones. Do not promise immediate remote logout.

## Exact shared wiring for main

1. Route `PORTAL_COMMANDS` through `portalCommand` with existing session token, Origin/CSRF defenses, rate/body bounds and stable command key. Do not allow client selection of provider parameters. Reconcile is a deliberate POST action; exclude this kind from automatic provider-write reconciliation.
2. Add dispatcher kind `billing_portal_create: portalEffect`. Its configured gate must require BILLING_PORTAL_ENABLED, STRIPE_ENABLED, the existing Stripe configuration, dedicated URL encryption configuration and kernel/journal/witness readiness. Preserve the shared intent/outcome journal and attempt-observe/resolve path. Adapter intent persistence is idempotent with that path; no raw provider object enters it.
3. Route authenticated status to `portalStatus`; render `portalViews({esc,dateTime}).panel(data,{org})` and wire form extraction through `portalFormInput`. Unauthorized callers get no customer-wide data; present a generic unavailable state rather than treating a missing grant as membership authority.
4. Route POST `/api/billing-portal/{id}/open` (or the reviewed equivalent) to `portalRedirect`, with original session and CSRF checks. Keep redirects out of access logs/analytics. The HTML deliberately contains no portal URL or third-party target.
5. Wire an explicitly reviewed owner setup/grant workflow to the server-only binding qualification and narrow grant RPC. Do not expose machine register functions through generic proxy endpoints. Configure existing objects first through a separately authorized process; this module never creates/repairs Stripe configuration.
6. Schedule `wm_portal_expire()` for ciphertext cleanup. Secret expiration already blocks disclosure even if cleanup is late. Keep unresolved operations visible; do not auto-requeue or fabricate session readback.
7. Runtime requires BILLING_PORTAL_ENABLED=true, PORTAL_KERNEL_VERSION=portal-v1, PORTAL_IDEMPOTENCY_QUALIFIED=true, exact STRIPE_SANDBOX_ID and PORTAL_RETURN_URL, plus dedicated retained PORTAL_KEYS/PORTAL_KEY_ID and the existing Stripe/independent-kernel configuration. These are qualification declarations, not proof supplied by opaque keys or labels. Do not enable flags merely to pass tests.
8. Apply the reviewed migration through normal CI/staging process. It wraps the existing latest begin/resolve functions, revokes predecessor aliases from all external roles, and preserves their original service-only grants. Recheck wrapper ordering if another module adds wrappers before integration. No old/applied SQL was edited.

## Backup, restore, closure and qualifications

Registry explicitly includes `portal_bindings`, `portal_grants`, `portal_requests` as historical tenant evidence and **excludes `portal_secrets` entirely**. Customer export whitelists must continue to exclude all portal internal tables and bearer material. Do not put secret ciphertext in shared operations, journal proof or backup-visible projections. Dedicated key separation and short local expiry do not remove ciphertext from physical project backups automatically; real physical-backup retention/key custody is a separate qualification boundary.

Main must amend frozen typed restore coverage/signatures for these four tables. Recovered bindings must be requalified, recovered grants/requests must stay inert, and no old kernel permit or session may replay. Do not restore portal secrets or private key material, resurrect current grants from historical rows, or weaken existing coverage validation. Shared authority generation/recovery gates remain authoritative.

Invoice-history access can include payment even with subscription changes disabled. A payment-method update, return redirect or portal session creation is not evidence of an invoice payment, earned work, verified service start, service amendment or closure. Continue existing verified billing webhooks/readback, explicit service agreement, cancellation, refund and closure workflows. This module changes none of those.

Unqualified boundaries: actual merchant/test/live/sandbox access and key permissions, production configuration response shape including pause flag, effective payment-method scope, real Stripe replay behavior/expiry, independently durable kernel hooks, browser/redirect/accessibility behavior, real Postgres concurrency and final account custody. Test fixtures do not prove those. No live session or configuration was created, no credentials read/generated, no remote migration, customer message, commit/push or release approval was performed.
