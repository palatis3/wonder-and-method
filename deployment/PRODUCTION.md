## Inquiry monitor and release preflight

The active Healthchecks.io receiver uses a one-hour period, a fifteen-minute grace period and email alerts. Production runs at minute 17 each hour. A genuine production cron receipt was observed on October 19, 2026; a saved local timestamp is historical evidence, not proof of a later deployment. Keep the receiver URL private. No synthetic/manual ping is a substitute for a real production scheduled receipt.

Before release, `npm run predeploy` inspects the production secret-name inventory and fails if HEALTHCHECK_URL, RESEND_API_KEY, OPERATOR_TOKEN or FINGERPRINT_SECRET is absent. It does not retrieve their values. HEALTHCHECK_URL is a remote Worker secret; requiring it in the local operator credential file would incorrectly block read-only operator access and is deliberately avoided. To replace the receiver, use the pinned Wrangler interactive secret command and verify its URL is HTTPS with no credentials; do not put the URL in a command, repository file or report.

A healthy scheduled run pings only when notification delivery checks pass. A stale send, manual-review record, exhausted notification budget, missing mail configuration or failed scheduled stage withholds that ping. Retention review is reported separately in operator status. Native Worker fetch uses manual redirects and rejects every 3xx response; never follow a redirect carrying the receiver token. Fixed failure codes are safe to record; URLs, request bodies, credentials and inquiry content are not.

After deployment, compare the authenticated runtime version with the returned deployment version, inspect aggregate inquiry health, and confirm the receiver's next scheduled receipt and alert destination in its dashboard. If overdue, inspect fixed scheduled diagnostic codes and the private operator queue, then check provider delivery and recipient inbox before retrying an inquiry. Never reset frozen requests or retry counters to force a send. Restore only a compatible known-good Worker; rolling back code does not restore D1. The receiver checks the scheduled worker and notification pipeline, while the website's route/asset checks separately verify public availability.

Notifications use a daily total budget of 50 attempts: new public submissions may consume at most 40, leaving 10 reserved for authenticated operator retries. Every attempt, including scheduled retries, remains bounded by the total cap and its per-record idempotency window.
